Prodject

I manage AI coding agents the way I would a small team. They build the work and check each other’s output. I write the requirements, approve what gets built and decide every merge. Then I test the agents themselves, with evals that show whether a change to how they work made them better or only felt like it.

Why I built it

Writing code is fast now. Knowing it works is the hard part.

AI agents write code faster than I can read it, and they report success with the same confidence whether or not it’s true. The question I care about is the one I ask on any client project: how do we know this works?

Prodject answers it with three habits I’d want on any team: requirements with testable acceptance criteria, a review step that has to show evidence, and measurement before and after every change to how the work gets done.

The team

Who does what

  • Me product owner

    I add ideas, answer the questions only I can answer, approve what gets built, and decide every merge.

  • The loop coordinator

    Breaks each idea into slices, pieces of work of about a day with acceptance criteria, hands approved slices to a builder, and limits how many are open at once.

  • Builder Claude Sonnet

    Builds one slice on its own branch: spec first, only the files the slice names, a new test for every feature with testable logic, then a summary built from real command output.

  • Checker Claude Haiku

    Reads the branch and marks each acceptance line as proven by a test (quoting it), visible only in a screenshot, or not shown. It never edits anything.

  • Scouts Claude Sonnet

    Read newly merged code looking for bugs and for features that don’t connect end to end, and propose at most three new cards a run. Each bug comes with a reproduction, or is flagged as one they couldn’t reproduce.

  • Analyst Claude Haiku

    Answers questions about eval runs from the saved results, and has to cite the runs it used.

Guardrails

What the agents aren’t allowed to do

  • Merge without me. Every slice waits for my call. Making that a hard lock, not just a rule, is next.
  • Guess at anything a user would notice. Names, copy, look and tuning numbers come back to me as a question with options and a recommendation.
  • Wander outside the slice. A guard script checks the branch name, the files touched, that the spec came first, and that no test was removed, skipped or narrowed. Editing an existing assertion is against the builder’s rules.
  • Grade their own homework. The checker is a separate agent on a different model from the builder, and it has to quote the test that proves each line.
  • Touch the release branch. Only I release.

Measuring the agents

How I measure the agents

Three of the roles have their own eval, all built the same way: known answers, several runs per case, and a 95% interval on every rate, so a change to how an agent works is judged against noise rather than a hunch.

  • Defect scout

    Nine bugs planted in real changes to one of my games, three runs each. It caught 21 of 27, and missed a replay of a real past bug every time (0 of 3). When I added an instruction to check each change more carefully, it caught 20 of 27: no clear change, so the instruction didn’t ship. A cleaner rerun is next.

  • Checker first run pending

    Its marks compared with my own merge and change calls on past slices from my board, with a model grader that has to agree with my hand labels before it’s trusted.

  • Analyst first run pending

    Five questions with answers I worked out from the data, scored right or wrong, with every cited run checked to exist.

What it shows

What it says about how I work

  • Writing requirements someone else can build from without guessing, with acceptance criteria a reviewer can check.
  • Designing review around evidence, not around trusting a confident summary.
  • Measuring AI quality with controls, repeated runs and intervals, and reporting a null result as plainly as a win.
  • Keeping a human in the decisions that matter while handing off everything else.
