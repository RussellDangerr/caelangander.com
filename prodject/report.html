Does the defect scout catch bugs I plant?

An evaluation of one AI reviewer, and what happened when I changed one thing about it.

What is measured

The defect scout reads the code that merged since its last look and proposes at most three defects. The eval asks one question: when I know a bug is there, how often does it say so?

How it is measured

  • Planted controls. Nine bugs, each folded into a real change so it looks like part of that change. Each imitates a kind of defect the scout found for real before.
  • A harness check. One blatant bug it should catch almost every time. It caught 3 of 3 before and 3 of 3 after, so the setup works.
  • Margins, not single runs. Every case runs three times. Rates carry a 95% interval (Wilson), and a change is compared with a second interval (Newcombe). If that interval includes zero, the page says there is no clear change, whatever the sign. These intervals treat every run as independent. Each case tends to go all or nothing, so the real margins are wider.
  • One change at a time. Only one block of the scout's instructions differs between the two sides. A later audit found most baseline runs used an older setup than the runs after the change, so a cleaner rerun is next.
  • Hand-checked. Every graded run was also read in full by Claude, not only scored by the code grader. My own labels on a sample are next.

One real before and after

The change: one added instruction telling the scout to check each changed hunk against its own comment, the spec line it implements and the test meant to catch it, before clearing it.

Before (baseline)21/27 = 78%95% interval 59–89%
After (added instruction)20/27 = 74%95% interval 55–87%

Change −4 points (95% interval −26 to +19): no clear change.
With about 27 runs a side, only moves of roughly 25 points or more would show. This one is well inside the noise.

What it tells me

  • The added instruction did not help. The misses did not move.
  • The misses were mostly not about looking in the wrong place: in nearly every miss the scout read the planted line and passed it.
  • On the clean ranges (real code with nothing planted) the scout made 1 proposal in 6 runs before and 4 in 6 after.
  • Next try: change what the scout must write down, not what it is told.
